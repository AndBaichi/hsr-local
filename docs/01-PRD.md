## 1. 产品定位与目标

### 1.1 一句话定义

**把《崩坏：星穹铁道》的全站资料库离线装进一个 Windows 桌面应用，用"查资料"的效率重新组织界面，而不是复刻网页。**

### 1.2 解决的问题

| 现状痛点 | 本地版的解法 |
|---|---|
| 原站是纯 SSR 网页，每次查资料要开浏览器、等水合、被网络波动影响 | 全量数据+图片打包进安装包，断网可用，切换页面无网络等待 |
| 原站界面为浏览型信息流，查找效率低（列表页→详情页→翻 tab） | 按资料工具重构：列表页内联筛选、详情页单屏密集信息、全局搜索直达 |
| 无法跨模块检索（想找"提到某角色的光锥/敌人"） | 全局索引跨 6 模块 × 4 语言全文检索，支持中英文与别名 |
| 无法并列比较多个角色 | 多角色对比页，属性/技能/星魂并排差异对照 |
| 无法做个人标记 | 本地收藏夹 + 自由笔记，重启不丢 |
| 版本更新需等站点维护 | 导入新版数据包即可，无需重装应用 |
| 只有网页，无桌面常驻入口 | 原生窗口、快捷键唤起、无浏览器标签污染 |

### 1.3 明确不做（边界，防止范围失控）

| 不做 | 原因 |
|---|---|
| 不做账号体系、云同步、多端同步 | 纯本地工具，无服务端 |
| 不做配队推荐 / 伤害计算器 / 遗器毕业度评分 | 属于"攻略计算"领域，非资料查询；数据链路也不同 |
| 不做抽卡记录导入、游戏客户端读内存 | 合规与技术风险高 |
| 不做社区、评论、UGC 内容 | 无服务端，且偏离定位 |
| 不做数据抓取器（爬虫） | 应用只**消费**数据包，抓取在应用之外完成 |
| 不做 1:1 复刻原站视觉 | 已确认为重新设计；且须避免版权风险 |
| 不使用官方 Logo / 立绘 / KV 作装饰性素材 | 仅使用数据包内的功能性图标（属性、命途、头像等） |
| 不做移动端、不做 Web 版 | 已确认形态为 Windows 桌面 |
| 不展示需要实时演算的内容（如角色模拟面板、等级成长曲线插值） | 静态数据不提供成长曲线，硬算会失真 |

### 1.4 目标（三个正交目标）

| # | 目标 | 可衡量结果 |
|---|---|---|
| G1 | **离线完整**：6 个模块、4 种语言、全部图片在无网络环境下 100% 可浏览 | 断网状态下遍历全部页面，无空白图、无请求失败、无降级提示 |
| G2 | **查询高效**：把"找到一条资料"的路径压到 ≤ 2 次交互 | 全局搜索任一实体名 → 进入详情；从详情到关联实体 ≤ 1 次点击 |
| G3 | **可持续**：数据可随游戏版本迭代而不重装 | 导入新数据包后，版本号更新、内容更新、用户收藏与笔记不受影响 |

### 4.5 图鉴与原站对齐（v2.3 新增）

> 本节为**新增能力与缺陷修正**，不改动 §3 任何既有需求 ID 的状态，也不影响 §6.3 断言与 §7.2 体积口径。

- 生命值 / 速度提高取 `general_property_modify_list` 里 `HPAddedRatio` / `SpeedAddedRatio` 的 `value × 100`（0.45 → 45%）；前台/后台基础强度取 `front_power_base` / `back_power_base`；治疗 / 护盾取 `extra_heal_base` / `extra_shield_base`。
- 技能标签源数据**中英混排**（`AoEAttack` 与「群攻」并存，实测 10 种语义、19 个写法）：先归一成英文枚举再翻译，映射不到回显原值 —— 换包出现新标签时不至于显示空白。

**边界**：不新增联网点（552 个详情文件是构建期一次性下载，运行期只读包内 JSON）、不新增权限面、不新增依赖；四语言新增 **33 个 key**（`currencyDetail` 段 19 项 + `tags` 10 项 + `statLabel` / `spCost` + `currency.healer` / `shielder`，parity **409 → 442**）；数据包条目 6802 → **7359**，压缩后 74.5 MB。

### 4.8 数据包升级自动重解（v2.6 新增）

> 追加节：不改 §3 需求 ID 状态，不改 §6.3 断言与 §7.2 体积口径。§4.7 的 v2.5 口径继续有效。

**问题（用户实机反馈）**：安装 v2.5 后点开任何角色，详情页一律显示「未找到该角色」。

**根因**：不是前端、不是路由，而是**解包目录被复用**。`.hsrpack` 作为安装包资源分发，首次启动展开到 `%APPDATA%<appId>\packs\<packId>\`，之后靠 `active.json` 指针走「快速路径」直接复用。原快速路径只校验两件事：指针里的 `packId` 与目录里 `meta.json` 的 `packId` 一致、`meta.schemaVersion` 兼容。而 v2.5 的新增是**552 个详情文件**：

- `packId` 是常量（`hsr-4.7.51-local`），不随内容变；
- 游戏版本仍是 4.7.51；
- `meta.counts` 只统计 6 个模块的条目数，详情文件不计入。

于是三项校验全过 → 继续用 6802 条目的旧目录 → `read_json("db/{lang}/currency/role/{id}.json")` 返回 `PACK_FILE_MISSING` → 前端统一显示「未找到该角色」。

实机证据（用户机器）：`packs/hsr-4.7.51-local/db/zh/currency/` 只有 6 个汇总 JSON，**没有 `role/` 子目录**；`active.json` 里也只有 `packId` / `root` / `gameVersion` / `schemaVersion` / `installedAt`，没有任何内容指纹。

| 项 | 原状 | v2.6 口径 |
|---|---|---|
| 指针字段 | `packId` / `root` / `gameVersion` / `schemaVersion` / `installedAt` | 追加 `archiveBytes`（压缩包字节数）与 `entryCount`（zip 中央目录条目数），二者构成**内容指纹**；`serde(default)` 兼容老指针 |
| 快速路径判定 | 仅比 `packId` + `meta.json` 存在 | 再加一道指纹比对：指纹一致才复用；**指纹缺失（老版本写的指针）或任一不符 → 重新展开** |
| 比对成本 | — | 只读 `fs::metadata` + zip 中央目录（文件尾部几 KB），**不解压任何条目**，冷启动代价可忽略 |
| 拿不到压缩包时 | — | 放行（返回「一致」），不因绿色版被删包而反复重解 |
| 重新展开的代价 | — | 一次性：7359 个文件、约 30–60 秒（Defender 实时扫描下），期间沿用既有解包进度条；完成后写入新指纹，**之后启动不再重解** |

**验证（实机，非推断）**：

1. 用旧指针 + 新二进制启动 → 出现 `packs/hsr-4.7.51-local.tmp`（解包暂存），完成后指针变为 `{"archiveBytes":78089854,"entryCount":7360}`，`db/zh/currency/role/` 出现 **138 个文件**，`.tmp` 目录被 rename 清掉；
2. **负向对照**：紧接着第二次启动 → `installedAt` 保持不变、无 `.tmp` 目录 → 快速路径生效，不重复解包。

**衍生收益**：老指针里 `installedAt` 未变但内容换了，是最容易长期潜伏的一类缺陷（此前每次数据包更新都要靠用户手动删目录）。指纹化之后，往后任何一次数据包内容更新都自带升级路径。

**边界**：不新增联网点、不新增权限面、不新增依赖；不改 `packId`（避免目录名变化留下 95 MB 残留）；不引入全量哈希（78 MB 逐字节读会在冷启动加几百毫秒）；副作用是**升级后首次启动会重解一次**，属必要代价，已在页内文案中明示。

**顺带修正的文案**：详情页拿不到详情时，原提示「链接可能已失效，或该地址尚未注册路由」会把人带偏（路由是通的，是数据缺）。改为区分两种缺失：图鉴汇总里没有该 id → 保留原提示；汇总有、详情文件缺 → 「数据包里没有这条角色的详情数据，若刚升级过应用请用最新安装包重新安装」。四语言同步（新增 `currencyDetail.missingInPack`，parity **442 → 443**）。

### 4.9 列表首字母索引（v2.7 新增）

> 追加节：不改 §3 需求 ID 状态，不改 §6.3 断言与 §7.2 体积口径。§4.4–§4.8 的既有口径继续有效。

**问题（用户实机反馈）**：资料库各列表页的卡片按数据包原始顺序排列（角色按 id、物品按 16 个分片序号、敌人按 `order`），顺序与名称毫无关系，除搜索之外没有第二个找东西的入口。

**需求**：①卡片按**标题首字的拼音首字母**排序；②右侧加一条**字母索引条**（形态对齐手机音乐 App 的 A–Z 索引），当前字母高亮成气泡。

| 项 | 口径 |
|---|---|
| 生效范围 | 角色 / 光锥 / 遗器 / 敌人 / 物品 五个列表页 + 货币战争五个分页图鉴（角色、装备、增益、强化、羁绊）；主角光环不分页但**同样按拼音排序**；**全局搜索结果不改**（保持相关度序） |
| 排序键 | 卡片标题**本地化后的显示名**。取「第一个有意义的字符」——跳过 《「【· 等前导标点与空白，数字开头（如 `3 星光锥`）按约定归 `#`，不往后找字母 |
| 分组 | 每个首字母一段，段头为「字母 + 该字母**全量**条数 + 细线」，**吸顶**跟随滚动 |
| 字母条 | 右侧竖排 `A`–`Z` + `#`（`#` 收数字/符号开头与未收录汉字）。点字母跳到该字母首条（**跨页**时自动翻页再定位）；按住可上下拖动连续跳转；当前段字母高亮成气泡；**该字母没有条目则置灰不可点** |
| 键盘可达 | 字母条每一项是 `<button>`，Tab 可聚焦、Enter 可触发（PRD §7.6 无障碍） |
| 每页条数 | `prefs.listPageSize` 此前是**空设置**（`PagedGrid` 写死 96，设置页改了不生效），本轮接上并成为唯一来源：20–200，默认 60 |

**四语言各自一套字母表**（不是把中文拼音表硬套到别的语言）：

| 语言 | 分组依据 | 字母条 |
|---|---|---|
| zh | 汉字查内置拼音首字母表；拉丁字母直接取大写 | `A`–`Z` + `#` |
| en | 标题首字母大写 | `A`–`Z` + `#` |
| ko | 谚文按 Unicode 初声 `(code - 0xAC00) / 588`；双辅音（ㄲ ㄸ ㅃ ㅆ ㅉ）并入基本音 | 14 个基本辅音 + `#` |
| ja | **不分组** | **无字母条**（仍按 `Intl.Collator('ja')` 排序） |

日文不做索引是刻意的：数据包里**没有假名读音字段**，637 个汉字首字无法判定五十音行；硬做只会把 86% 的条目塞进「他」组，反而不如不给。

**拼音表口径**：只收录数据包 4.7.51 里**实际作为首字出现过**的 839 个汉字（`src/lib/text/pinyin-initials.generated.ts`，约 2.6 KB），不做通用汉字表——未收录的字落到 `#` 组，不崩、只是排后面；换包后若新增首字，重跑生成脚本即可。多音首字按游戏内语境人工裁决（「长」→ c：长夜月 / 长路终有归途；「重」→ c：重返幽冥 / 重塑时光之忆），其余取 pypinyin 默认读音。

**验证**：拼音表用两套独立实现交叉验证——`pypinyin` 取首字母 vs `Intl.Collator('zh-Hans-CN-u-co-pinyin')` 全排序后检查同字母组是否连续，839 字中仅「蕃」（bō / fán 两读）一处分歧。

### 4.10 列表全量渲染与滚动位置记忆（v2.8 新增）

> 追加节：不改 §3 需求 ID 状态，不改 §6.3 断言与 §7.2 体积口径。§4.9 的拼音排序与字母条口径继续有效，本节只把「分页」这一层拿掉。

**问题（用户实机反馈）**：列表每页 60 条，导致两种割裂——①翻页是「换一屏内容」，浏览长列表时被反复打断；②点字母条若目标字母不在当前页，要先翻页、等渲染、再滚到段头，是两段式跳转，落点还会闪一下。用户原话「直接都不分页了吧」。

**方案**：`PagedGrid` 全量渲染（组件名为历史遗留，保留以免六个调用点无谓改名）：

- 删掉页码状态、页码条、`pageSize`/`nextLabel`/`prevLabel` 入参与「先翻页再定位」的 `pendingSymbolRef` 两段式逻辑；
- 字母条点击退化为**一次 `scrollBy`**：全量渲染后每个段头都真实存在于 DOM，`getBoundingClientRect()` 拿到的就是真实位置；
- 分段标题的条数不再分「本页条数 / 全量条数」两个口径，段内条数即全量条数；
- **顺带移除已失效的「列表每页条数」设置项**（设置页 UI），避免再次制造空设置；`prefs.listPageSize` 字段与其 clamp 逻辑保留不动，以兼容用户已有的 `prefs.json`（删字段会破坏反序列化），`settings.pageSize` / `settings.pageSizeDesc` 两个 i18n key 四语言同步保留（无 UI 引用，parity 不变）。

**滚动位置记忆（同轮追加，用户确认）**：从详情页返回列表时恢复离开前的滚动位置，否则全量列表里点第 1200 条进详情、返回后被甩回顶部，比分页时代更难受。实现为模块级 `Map<路由路径::条件指纹, scrollTop>`，会话内有效、不落盘。两个关键实现约束：

1. 保存必须用 `useLayoutEffect` 的清理函数——`useEffect` 的清理在 DOM 移除**之后**才执行，此时 `<main>` 内容已被掏空、浏览器把 `scrollTop` 钳成 0，存下来的永远是 0；
2. 恢复用直接赋值 `scrollTop` 而非 `scrollBy({behavior:'smooth'})`，返回列表不该有一段「从顶部滑回去」的动画；
3. 条件指纹（搜索词 + 筛选值）参与 key：搜索状态下停的位置不套用到未搜索状态；指纹变化仍走既有的「滚回列表顶」逻辑，二者不冲突。

**为什么不用 `content-visibility` / 虚拟滚动**：两者都靠「估算高度 + 跳过渲染」省开销，会让段头的 `getBoundingClientRect()` 返回估算位置，字母条跳转会落错地方（段落越高偏差越大）；虚拟滚动还会让未渲染段的段头直接不存在。字母条是本列表的主导航，不能为了省几十毫秒把它做坏。改为：

- 条目走 `useDeferredValue`，搜索框逐字输入时把重渲染降为可中断的低优先级更新，输入框始终即时响应；
- 图片沿用 `loading="lazy"` + `decoding="async"`（`SafeImage` 既有行为）；
- 滚动高亮保持 rAF 节流，段头数量最多约 30 个，逐次 rect 读取成本可忽略。

**量级依据**：最大列表为物品 1606 条（约 1.4 万 DOM 节点），敌人 666 条，其余数百条；全量铺开是一次性布局成本，滚动过程没有 per-item JS。

**验证**：typecheck 0 错、`vitest` 100 passed；实机验收点见架构文档附录 C 第 25 项。

**边界**：不新增联网点、不新增权限面、不新增依赖（`useDeferredValue` 是 React 19 自带）；不新增 i18n key（parity 保持 **444**）；成就页与全局搜索本就不分页，不受影响；主角光环大卡本就不分页，仅沿用 §4.9 的排序。

### 4.11 对比 / 收藏 / 笔记扩展与卡片右键菜单（v2.9 新增）

**ADDITIVE ONLY**：本节追加 v2.9 的工具组件增强，不改变 v1.6 冻结需求 ID（P0-xx）的状态与措辞，不触碰 §6.3 断言、§7.2 体积口径，§4.9–§4.10 的既有口径继续有效。

2. **旧数据迁移**：`coercePrefs` 把无冒号的旧格式按「角色 id」升级为 `character:{id}`，模块前缀不在白名单的脏数据直接丢弃，不整份推翻 prefs。
3. **卡片右键菜单**：资料库卡片（五个列表页 + 成就系列头）右键弹出「打开详情 / 加入对比（或移出）/ 加入收藏（或取消）/ 记录笔记」。收藏/笔记借此获得列表页入口，数据层六模块支持为既有能力，无 schema 变更。成就系列无详情路由，菜单不显示「打开详情」。对比已满（10 个）时「加入对比」置灰并提示。
4. **笔记弹窗**：右键「记录笔记」就地弹窗编辑，与详情页 `DetailTools` 共用 notes store（600ms 防抖落盘），两处内容互通。
5. **默认右键菜单抑制**：全局拦截 `contextmenu`（输入框/文本域/contentEditable 除外，那里保留系统菜单用于复制粘贴），默认菜单整体不再出现。
6. **边界**：货币战争（`currency`）不在 `ModuleKey` 内，本轮不支持收藏/笔记/对比；对比选择器候选上限 40 条防一次铺出整个物品索引。

**i18n**：新增 9 个 key（`compare.colType`、`contextMenu.*` ×7、`noteDialog.title`），parity **444 → 453**；`compare.title/sub/add/addHint/empty/selectPlaceholder` 四语言文案由「角色」改为「实体」。

**验证**：typecheck 0 错、`vitest` 100 passed；实机验收点见架构文档附录 C 第 26 项。

## 5. UI 设计方向

### 5.1 视觉基调

**深色为默认**。整体气质：冷峻、精密、克制的科幻仪器感 —— 深空底色 + 极细描边 + 少量冷光强调，**不使用任何官方美术素材做装饰**（不用立绘、不用 Logo、不用纹理贴图），所有装饰仅由 CSS 渐变、描边、透明度层次实现。

| 维度 | 深色（默认） | 浅色 |
|---|---|---|
| 应用底色 | `#0B0E14` | `#F6F8FB` |
| 卡片/面板 | `#131A24` | `#FFFFFF` |
| 浮层/悬停 | `#1B2431` | `#EEF2F8` |
| 分隔线/描边 | `#232E3D` | `#E1E7F0` |
| 主文字 | `#E7ECF4` | `#141B26` |
| 次文字 | `#8B96A8` | `#5B6577` |
| 强调色（主） | `#5FD3F3`（冰蓝） | `#0C8FB8` |
| 强调色（辅） | `#A78BFA`（星紫） | `#6D4FD1` |
| 稀有度金 | `#F2C14E` | `#B8860B` |
| 危险/警告 | `#F87171` | `#C0392B` |

- **稀有度**：★★★★★ 用金 → 紫的线性渐变边框；★★★★ 用紫色单色；★★★ 用蓝色单色。数值一律配 `tabular-nums`。
- **属性色标**（物理/火/冰/雷/风/量子/虚数 7 类）：从数据包 `element` 图标取色为主，统一叠加 64% 不透明度的图标底盘，保证深色下可读。命途图标同理。**具体色值不在 PRD 硬编码，由属性图标自身的色相推导，避免与官方视觉规定冲突。**
- **无衬线字体**：中文 `HarmonyOS Sans SC` → `Microsoft YaHei UI` → `system-ui`；拉丁/数字 `Inter` → `Segoe UI`。标题字重 600，正文 400，最小正文 13px，表格 13px。
- **间距**：4px 基准网格，常用 8 / 12 / 16 / 24 / 32。卡片圆角 12px，按钮 8px，标签 6px。阴影极浅（深色下用 `0 1px 0 rgba(255,255,255,.04) inset` + 1px 描边替代投影）。
- **动效**：仅用于状态反馈，时长 120–180ms，`ease-out`；不使用视差、粒子、发光呼吸等装饰性动效。

### 6.1 资源路径规则（图片）

> 全部路径已完成可达性实测（见 §0.1 D5/D6/D7）。打包时统一落到应用内 `img/` 目录，运行时只拼 `img/` 之后的相对路径。

| 用途 | 源站路径 | 应用内路径 | 使用位置 |
|---|---|---|---|
| 角色头像 | `avatarshopicon/{id}.webp` | `img/avatar/{id}.webp` | 角色列表/详情/对比/搜索结果 |
| 光锥卡面 | `lightconemediumicon/{id}.webp` | `img/lightcone/{id}.webp` | 光锥列表/详情/对比 |
| 敌人缩略图 | `monstermiddleicon/**Monster_**{id}.webp` | `img/monster/{id}.webp` | 敌人列表/详情 |
| 敌人全尺寸图 | `monsterfigure/Monster_{id}.webp` | `img/monster-figure/{id}.webp` | 敌人详情头部（可选，P2） |
| 物品图（小图标 / 立绘 / 遗器套装图标**三者共用**） | `itemfigures/{basename}.webp`，basename 取自 `item_icon_path`（`SpriteOutput/ItemIcon/900001.png`）**或** `item_figure_icon_path`（`SpriteOutput/ItemFigures/900001.png`）**或** 遗器 `icon`（`SpriteOutput/ItemIcon/71000.png`）——三者 basename 相同、落地同一个 webp（实测均 200） | `img/item/{basename}.webp` | 物品列表/详情、掉落网格、遗器列表/详情 |
| ~~货币图标~~ | `itemcurrency/*.webp` 与 `itemfigures/1.webp` 均 **404** | **不使用** | `item_currency_icon_path` 字段一律忽略 |

| 命途图标 | `pathicon/{path}**.toLowerCase()**.webp` | `img/path/{lower}.webp` | 全局（角色/光锥命途） |

**五条必须遵守的硬规则（来自实测，写错就是破图）：**

1. **属性/命途图标名必须全小写** —— `fire.webp` ✔ / `Fire.webp` ✘（404）；`knight.webp` ✔ / `Knight.webp` ✘（404）。构建期应断言 7 张属性图标 + 9 张命途图标全部存在且非 0 字节。
2. **敌人图必须带 `Monster_` 前缀** —— 裸 id 404。
3. **遗器套装图标与物品图共用 `itemfigures/`**，不要把 `SpriteOutput/ItemIcon/71000.png` 整条路径拼进 URL，只取 basename。
4. **物品的"小图标"与"立绘"是不同源目录（`ItemIcon` / `ItemFigures`）但 basename 相同**，都落到同一个 `itemfigures/{basename}.webp`，不要按目录名分流到两个文件夹。**`item_currency_icon_path` 不可用（实测 404），一律忽略。**
5. **遗器套装图标复用物品图通道，不新增独立资源类型** —— 路径解析只保留 `character / lightcone / monster / item / element / path` 六种，遗器走 `item`。集中到单一解析入口（不散落字符串拼接），避免各页面各写一套。

图片通用要求：本地文件直接读取（不经过 HTTP），`loading="lazy"`、尺寸由容器固定（避免布局抖动）、缺失时渲染统一占位（灰底 + 模块图标），失败不阻塞渲染。

### 6.3 富文本格式化规则（P0-05 的实现依据）

> **规则覆盖口径**：以架构师对**全量 4.7.51 JSON 的词法扫描**为准（覆盖全部 6 个模块 × 4 语言），以下共 **6 项新增标记 = 5 种占位符 + 1 种标签**。
> ⚠️ 注意：本表早期版本曾按"4 类"表述，且计数取自**物品模块子集**（如 `{TextID#…}` 记 29 处）。**全量口径的计数更大，一律以本版为准**（见下表括号内数字）。

**A. 全量扫描新增的 6 项（必须处理，否则页面漏出裸占位符）**

| # | 原始标记 | 全量出现次数 | 含义 | 处理规则 |
|---|---|---|---|---|
| 1 | **`{NICKNAME}`** | **93** | 玩家昵称占位 | 替换为当前语言的默认称呼（zh=`开拓者`、en=`Trailblazer`、ja=`開拓者`、ko=`개척자`）；**不引入用户自定义昵称设置**（P2 再议）；不得原样输出花括号 |

**B. 既有标记（延续 v1.0 规则）**

| 原始标记 | 含义 | 处理规则 |
|---|---|---|
| `<unbreak>` / `</unbreak>` | 禁止断行提示 | **直接移除标签**，保留内部文本 |
| `<color=#RRGGBB>…</color>` | 着色 | 转 `<span style="color:#RRGGBB">`，保留色值；深色主题下若对比度 < 3:1 则提亮 20% |
| `{RUBY_B#注音}汉字{/RUBY}` | 日文注音 | ja 语言下渲染 `<ruby>`；其他语言剥离注音块仅保留汉字 |
| `\n` | 换行 | 转 `<br/>` |
| `#n[spec]` | 参数占位 | **`n` 从 1 开始，取 `param_list[n-1]`**。`spec` 取值：`i` 整数｜`i%` ×100 取整加 `%`｜`f1`/`f1%` 1 位小数｜`f2`/`f2%` 2 位小数｜`m` 紧凑数字。**`%` 也可能写在方括号外**（形如 `#4[f2]%`），`[i%]` 与 `[f2]%` 两种写法都要支持。**越界（n > param_list.length）保留原文并告警，构建期告警非 0 拒绝出包** |
| `<b>` `<i>` `<u>` | 粗/斜/下划线 | 映射同名标签 |
| `%s` | 运行时填空 | 保留原文并按强调色高亮（不猜内容） |
| 其他未知 `<tag>` | 未知 | **剥离标签、保留文本**，开发模式打印警告清单 |

> **验收方式**：写一个一次性脚本，对全量 4.7.51 数据的所有文本字段（`desc` / 技能描述 / 套装效果 / 故事 / `item_desc` / `item_bg_desc` / `item_comefrom[].desc` 等）跑清洗管道，断言输出中 `<...>` 与 `{...}` 残留数为 0。
> **专项断言**：① `{F#…}{M#…}` 输出中不得同时出现两个分支，且**默认分支必须为 F**（**判定依据：渲染后的文本中性别分支位置呈现女性版本用词；不引用架构文档字段值**）；② `{TextID#…}` 按上下文处理（列表项整条丢弃 / 正文替换 `…`），花括号不得残留；③ `{NICKNAME}` 不得原样出现；④ `<align>` 不得作为正文出现；⑤ **构建期对清洗后文本再跑一次残留扫描，未消费的 `{` 记为 `unknown macro` warning，warning ≠ 0 即拒绝出包**；⑥ `#n[m]` 输出必须是 compact 格式（如「100万」/「1M」），**不得为裸数字「1000000」**。

> **宏清单的完备性不靠人工承诺**：当前实测共有 **7 种宏** —— `RUBY_B` / `RUBY_E` / `NICKNAME` / `F#` / `M#` / `TextID#` / `TEXTJOIN#`（`<align>` 属标签不属宏）。**本 PRD 不承诺该清单永久穷尽**；若源站将来新增第 8 种，由上述构建期残留扫描在第一次跑 validate 时拦下。工程师只需保证"流水线对未知宏告警并阻断出包"，不需要预判未来。

> **字段命名陷阱**：`param_list` 在**遗器套装列表文件 `relicset.json` 中写作 `ParamList`（唯一大写 P）**；其余位置（角色 `param_list`、遗器详情 `require_num.*.param_list`、光锥 `refinements.level.*.param_list`、成就 `param_list`）均为小写下划线。构建脚本读取时需兼容两种拼写。

### 7.2 离线与体积

| 项 | 要求 |
|---|---|
| 离线完整性 | 安装后**首次启动会在 10 秒后发起一次更新检查**（数据包 + 应用，24h 节流，失败静默）；**游戏数据、图片、搜索索引与数据包读取全程本地**，不访问原站；联网点仅：更新检查、首页公告/资讯、用户手动检查 |
| 图片 | 全部内置本地，无远程 URL 回退 |
| **数据包体积（实测基线）** | **≈ 85MB** = 80MB 基线 + **`item_all.json` 四语言 ≈5.8MB**（1.46MB × 4）。构成：数据 ≈23MB + 图片 ≈62MB。远低于初版预估的 300–500MB，因为源站图片为 WebP 且单张仅 12–103KB |
| **安装包体积** | **≤ 150MB**（实测预估 ≈65MB，含内置数据包与 WebView2 引导）；**上限从 600MB 下调至 150MB**，实测差 6 倍 |
| 安装后占用 | **≤ 300MB**（含数据包、图片、用户数据 + 更新保留的上一版本备份；原 ≤1.5GB 上限相应下调） |
| 首次启动 | 不需要下载、不显示"正在同步数据"类加载页 |
| 体积余量承诺 | 当前实现留有 ≥2 倍余量：即使后续版本内容翻倍，也不必改架构或改打包策略 |

> **v1.8 追加说明（历史；v2.21 已把启动更新检查纳入联网点）**：上表「离线完整性」的「首次启动不发起任何网络请求」**对游戏数据、图片、全局搜索索引与数据包仍然成立**。v1.8 新增的**唯一运行期联网点**是首页「公告」「资讯」两张卡——它实时拉取米游社公开接口 `https://bbs-api-static.miyoushe.com/painter/wapi/getNewsList`（`gids=6`，`type=1` 公告 / `type=3` 资讯，每类 5 条，8s 超时），**仅 `prefs.lang === 'zh'` 时渲染并发请求**；请求失败或断网时回退本地缓存（localStorage 键 `hsr.news.cache.v1`）并标注「缓存」，无缓存则显示「暂时无法获取 + 重试」，**不阻塞首屏、不轮询、不影响任何离线功能**。因此「零网络请求」的准确口径是：**除用户显式点击「检查更新」（P1-09）与首页「公告 / 资讯」卡片外，全程零网络访问**。设计与降级链路见 `docs/02-architecture.md` §13，运维与验收口径见 `README.md` §6.6。

> **口径说明**：本节 ≈85MB / ≤150MB 为**用户视角的验收量级参考，不作为构建期断言基准**。构建期校验一律以 `datapack-report.json` 中的实测值为准（当前约 80.4MB）。**两者的差异属于统计口径不同（是否含四语言 JSON、是否 minify），不是缺陷，也不得通过调整任何一方来"消除差异"。**

> **⚠️ 关于 150MB 这个数字的性质**：**150MB 是当前版本（数据 4.7.51）的实测值 + 余量，不是架构上限。** 数据包结构按「版本目录可替换」设计，**未来内容增长到 300MB 也不需要改架构**，只需按新版本重新测量并更新本表中的数字。请勿把它当作硬性架构约束来限制后续版本的数据采集范围 —— 本应用的价值在于完整离线，而非压缩体积。

> 说明：初版 PRD 的 300–500MB 是基于"用户不敏感"的保守上界，实测后确认实际远低于此。**下调上限不是降低要求，而是把验收标准校准到真实值**，避免"体积达标"变成无意义的通过项。

| 项 | 要求 |
